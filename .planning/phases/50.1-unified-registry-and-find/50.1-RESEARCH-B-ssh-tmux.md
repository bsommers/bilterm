## 1. Headline findings (read these first)

1. **There is no `:tmux` command and the `tmux -CC` bridge is not reachable from production code.** `TmuxControlSubprocess::spawn_attach_or_new` (`src/tmux/mod.rs:347`) and `WindowManager::attach_tmux_control` (`src/tmux/mod.rs:411`) have exactly one non-definition caller: a test (`tests/vt_worker_and_snapshot_seam.rs:284`, uses `from_channels`). `poll_tmux_control` is polled every tick (`src/wm/mod.rs:717`) but `tmux_control` is always `None` at runtime. Likewise `TmuxControlBridge::route_prompt_submission` (`src/tmux/mod.rs:302`), `queue_split` (`:318`), `queue_resize_client` (`:326`) have no callers outside `src/tmux/mod.rs`. [VERIFIED: grep + Read of src/tmux/mod.rs, src/wm/mod.rs]
2. **`:ssh-tmux` / `remote.connect_tmux` spawn nothing.** `connect_ssh_tmux` (`src/wm/session.rs:247-281`) splits a pane (`split_focused`, which spawns a plain local shell when not headless, `src/wm/mod.rs:621-630`), retitles it `TMUX-SSH:<dest>/<session> [#id]` (`:265`), sets `remote_target = "<dest>/<session>"` (`:266`) and registers a `FleetNodeKind::SshTmux` node (`:278`). `RemoteHostProfile::build_ssh_tmux_cc_args` (`src/remote/mod.rs:138-159`) is never called outside tests. The pane is a local shell wearing a remote badge. `docs/user-guide/05-tmux-integration.md:38` claims `TmuxControlSubprocess::spawn_remote_ssh_attach_or_new`; that symbol does not exist anywhere in the repo (grep). [VERIFIED]
3. **`remote_osc133_bootstrap` is a dead flag.** The profile field (`src/remote/mod.rs:38`) and `remote_osc133_bootstrap_command()` (`:164-166`) are referenced only by tests (`tests/full_suite_battle_and_perf.rs:21,77`, `tests/slide_out_drawer_and_telemetry.rs:532`); `spawn_ssh_pane` never reads it. [VERIFIED]
4. **Command capture today is purely local-submission based.** One choke point: `CompositePane::submit_command` calls `vt.record_command_submission(cmd)` and `history_store.record_command(cmd)` (`src/pane/mod.rs:214-215`). That works identically for local, SSH and (headless) tmux panes, because the floating prompt is local (`docs/user-guide/05-tmux-integration.md:37`). Nothing records host, session or remote cwd with the command (see 3.3).
5. **Only the headless daemon is a hard no-op for SSH.** With `--headless`, `AutomationControlPlane::new_headless` builds a `WindowManager::new_headless` (`src/main.rs:249`, `src/wm/mod.rs:539-542`), so `spawn_ssh_pane` skips the PTY spawn (`src/wm/session.rs:213`) and registers a fleet node and badge for a pane that has no `ssh` process. Registry data for those panes is metadata only.

## 2. How each thing is represented in WindowManager

### 2.1 Direct SSH (`:ssh`, `remote.connect_ssh`)
- `spawn_ssh_pane` (`src/wm/session.rs:181-244`): resolve profile from `fleet.profiles` then `config.remotes` then ad-hoc `RemoteHostProfile::new(target, target)` (`:187-193`); `ssh -tt [ControlMaster opts] [-p] [-i] -- <dest>` (`src/remote/mod.rs:125-132`); `CompositePane::spawn` with `program: "ssh"` (`:219-226`); title `SSH:{dest} [#{id}]` (`:228`); `set_remote_target(Some(dest))` (`:229`); fleet node name `"{profile.name}-#{id}"` (`:240`) via `register_ssh_pane` (`src/remote/mod.rs:291-313`).
- It is an ordinary `CompositePane` in `WindowManager.panes` (`src/wm/mod.rs:95`) plus a `FleetRegistry` entry (`WindowManager.fleet`, `src/wm/mod.rs:108`). The pane has no structured transport field; the only per-pane marker is `remote_target: Option<String>` (`src/pane/mod.rs:71`, accessors `src/pane/scroll.rs:571-577`), a free string: `"user@host"` for SSH, `"user@host/session"` for ssh-tmux (`src/wm/session.rs:263`). Consumers split on `/` (`src/wm/drawer/navigator_detail.rs:20`).
- A user who types `ssh host` inside a plain local pane gets **no** `remote_target`, no fleet node and no badge; only `resolve_running_command()` (`src/pane/scroll.rs:633-`, `/proc/<fg_pgid>/cmdline`) can reveal it.

### 2.2 `:ssh-tmux`
As above (finding 2): `FleetNodeKind::SshTmux { destination, session_name, pane_ids }` (`src/remote/mod.rs:211-215`), node name `tmux-{dest}-{session}` (`src/wm/session.rs:277`). `pane_ids` always has exactly one entry. Nothing ever adds the remote tmux's other panes.

### 2.3 Local `tmux -CC` bridge (Phase 11 code in `src/tmux/mod.rs`)
- Two singletons on `WindowManager`: `tmux_control: Option<TmuxControlSubprocess>` and `tmux_bridge: TmuxControlBridge` (`src/wm/mod.rs:126,128`). **One tmux session at a time**; no per-session key.
- `TmuxControlBridge` (`src/tmux/mod.rs:236-244`): `tmux_to_bilterm` / `bilterm_to_tmux` (`%pane_id <-> PaneId`), `active_session_name`, `outbound_commands`, `exited`. `new()` hard-maps tmux `%0` to Bilterm pane `1` (`:248-251`).
- `insert_tmux_pane` (`src/wm/v2_runtime.rs:72-94`) creates a **headless** `CompositePane` (no PTY) titled `TMUX %{id}` (`:84`). `%output` is unescaped and fed via `process_pty_output` (`src/tmux/mod.rs:275-280`).
- Events parsed (`src/tmux/mod.rs:53-74`): `Output`, `WindowAdd`, `WindowClose`, `WindowPaneChanged`, `LayoutChange`, `SessionChanged`, `Exit`, `BeginBlock`, `EndBlock`, `Other`. Only `session name` (from `%session-changed`) and the pane-id set (from `%layout-change`) are retained. **Dropped:** `window_id` in every window event (no pane-to-window map), window names (`%window-renamed` falls through to `Other`), `$session_id`, `%begin/%end` payload lines and the command number (so command replies cannot be correlated), `%error`, `%sessions-changed`, `%session-renamed`, `%pane-mode-changed`, `%extended-output`/`%pause`/`%continue` (flow control), `%subscription-changed`.
- Transport badge detection is title based: `pane.title().contains("TMUX") || is_tmux_control_attached() || fleet SshTmux` (`src/wm/drawer.rs:539-544`).
- Outer `$TMUX` (`TmuxEnv`, `src/tmux/mod.rs:7-42`) only describes the tmux that *contains Bilterm* (`socket_path`, `server_pid`, `session_id`); used for leader-key fallback and OSC 52 DCS wrapping (`src/app.rs:116`, `src/input/keymap.rs:598`). It is not a pane source.

### 3.2 Limits and failure modes (document these)
- **Remote shell without integration:** no OSC 133 -> no exit code/duration, no prompt boundaries; `pane.is_password_prompt()` falls back to termios heuristic (`src/pty/line_discipline.rs:55-110`). With `ssh -tt`, the local PTY is raw (ECHO/ICANON off) and the foreground pgid equals the shell (ssh) pgid, so `has_foreground_subcommand()` is false; the heuristic's `shell_owns_tty` branch treats a !ECHO state without OSC 133 `C` as a normal prompt (`line_discipline.rs:~125-140`). Consequence: floating prompt stays up and C1 keeps working for plain SSH shells, but anything typed *inside* a remote program (python REPL, `mysql>`) is also logged as a "command".
- **Remote cwd:** correct only with remote OSC 7 or the bootstrap (dead). Never trust `resolve_cwd()` for `remote_target.is_some()`; `navigator_detail.rs:19-24` already special-cases this and the registry must do the same. Also `track_submitted_command_state` applies `cd` to the *local* `tracked_cwd` using local `$HOME` (`src/pane/scroll.rs:672-694`), polluting cwd for SSH panes.
- **Full-screen apps (vim, htop, tmux client itself):** alt screen -> `RawPtyPassthrough` (`src/pane/mod.rs:627-637`); keystrokes bypass `submit_command`; nothing is captured (by design). A user running `tmux` by hand in a pane (local or over ssh) shows only the tmux client's rendered UI; Bilterm cannot see its sessions/panes without querying the tmux server separately.
- **Password prompts:** `ssh`'s own password/passphrase prompt (!ECHO + canonical) triggers raw mode and `is_password_prompt()`; `submit_command` is bypassed for raw keystrokes, `exec_fleet_command`/`broadcast_command` skip such panes (`src/wm/session.rs:333-336`, `src/wm/v2_runtime.rs:46`), and `pane.exec` requires `allow_echo_lock` (`src/api/rpc.rs:311`). **Registry must never store raw-mode keystrokes or output rows while `is_password_prompt()`**, and `pane.exec(..., allow_echo_lock=true)` payloads should be flagged and skipped (the traffic bus already redacts: `src/wm/traffic.rs:24`; history store does not, `src/pane/mod.rs:215`; verify when wiring).
- **Multi-line / paste:** a single history record escapes `\n`/`\r` (`history_store.rs:55-65`); `;`-chained commands are one record.
- **tmux `%output` is not commands** (C4). Octal-escaped bytes below 0x20 and backslash (wiki).
- **Latency/ordering:** tmux control commands are asynchronous; replies arrive between `%begin`/`%end` (or `%error`) guard lines with a command number (wiki). Current parser discards the reply body (`TmuxControlEvent::BeginBlock/EndBlock` carry no data; `Other(line)` is not tied to a block), so `list-panes -F` over `-CC` needs a small reply correlator that does not exist.
- **`ssh -T` for tmux -CC:** `build_ssh_tmux_cc_args` uses `-T` (no remote TTY) (`src/remote/mod.rs:144`). The wiki states `-CC` is intended for applications and disables canonical mode, and does not state a tty requirement; whether `tmux -CC new-session -A` works without a remote tty is **not verified** [ASSUMED works]. The docs claim `ssh -tt` (`docs/user-guide/05-tmux-integration.md:38`), which contradicts the code. Resolve with a live probe before wiring.
- **Flow control:** no `refresh-client -f pause-after`; a slow client with a chatty pane is unbounded (wiki). Not a registry blocker but affects completeness of any `%output`-derived index.

### 3.3 What is missing in the existing record formats
- `HistoryEntry` / `HistoryStore` (`src/pane/history_store.rs:95-103,389-396`) carry only `timestamp, session, run_id, pane_id, command`. No host, user, transport, tmux session/window/pane, cwd, exit code, duration. `pane_id` is only unique within a run (`run_id`), so cross-run find must key `(run_id, pane_id)`.
- `CommandBlockRecord` (`src/vt/mod.rs:39-45`) has `index, command, absolute_row, exit_code, duration_ms`; no timestamp, no cwd, no host; in-memory and pruned with scrollback.
- `SavedPaneState.history` / `PaneJournalRecord.command_history` are bare `Vec<String>`.

## 4. Headless / daemon / attach implications

- `bilterm --headless` (`src/main.rs:244-276`): JSON-RPC/HTTP control plane around a **PTY-less** `WindowManager`. SSH/tmux/fleet calls (`remote.connect_ssh`, `remote.connect_tmux`, `fleet.*`; `src/api/rpc.rs:37-42`) succeed in creating metadata but never run `ssh`; the only live data there comes from `pane.feed_output` (`rpc.rs:31`) or tests. A registry in headless mode is a view of whatever was fed. The `fleet.list` JSON exposes only `name, connected, tags, last_command` (`src/api/rpc.rs:647-672`): no destination, kind, pane ids or session name; the registry JSON should be a superset.
- `bilterm daemon` / `attach` (`src/daemon/mod.rs`, `src/main.rs:384-503`): `DaemonSessionSummary` (`src/daemon/mod.rs:40-49`) lists session name/kind/pane_count/clients only; checkpointing uses `PaneJournalRecord` (no `remote_target`). `spawn_background_daemon_for_session` and `attach` restore layout; ssh/tmux live PTYs are not preserved across detach in a way the registry can rely on `[ASSUMED]` (Phase 35 PLAN.md was not found at `.planning/phases/35-live-pty-background-daemon-attach/PLAN.md`; only `35-PLAN.md` exists and was not read). Consequence: **registry must be reconstructable from `WindowManager` state + persisted history, never from in-process subscriptions only**, and a `live: bool` flag per row is needed (the Navigator already has `NavigatorRowMeta.live`, `src/wm/drawer/navigator.rs:68-70`).
- Persisted history is the only cross-process find source: `<state>/bilterm/history/sessions/<name>/history.log` (`history_store.rs:176-186`, `default_history_dir`). That file is shared by all panes/runs of a named session, so `:find cmd` can search it directly; adding fields must stay backward compatible with `parse_history_line` (`:108-130`, ignores unknown `|` fields; header is split on `" | "`, so new `key=value` fields are safe).

## 5. Recommendation: how each source plugs into a unified registry

Design rule: **one `RegistryEntry` per Bilterm `PaneId` (the key the whole app already uses), with an optional `transport` descriptor and an optional list of *child* entries for tmux panes that are not (yet) Bilterm panes.** Derive entries on demand from `WindowManager` (cheap, `BTreeMap<PaneId, CompositePane>`); only history/command indexes persist.

### 5.1 Entry schema (superset)
```
pane_id, run_id, session (bilterm session name), title, window_title,
transport: Local | Ssh{dest, user?, host, port?, profile?} | SshTmux{dest, session, tmux_pane?, tmux_window?}
          | TmuxCC{session, tmux_pane, tmux_window?}   // local control mode
fleet_node?, tags[], cwd{value, source: osc7|proc|tracked|none, trusted: bool},
running_command?, agent{state,profile?}, live, read_only, password_prompt,
integration{osc133: seen|never, osc7: seen|never}
```
`cwd.trusted=false` whenever `transport != Local` and the value did not come from OSC 7 (reuse the `navigator_detail.rs:19-24` rule; do not call `resolve_cwd()` blindly).

## 6. Gaps to document explicitly (user-visible "Known limits")
- **G1** `tmux -CC` control mode is implemented and unit-tested but not wired to any command (no `:tmux`); `route_prompt_submission` is unused. Only one tmux session supported by the bridge. [VERIFIED]
- **G2** `:ssh-tmux` does not start tmux; the pane is a local shell with a remote label; `docs/user-guide/05-tmux-integration.md:38` is wrong (`spawn_remote_ssh_attach_or_new` does not exist; `-tt` vs `-T` mismatch). [VERIFIED]
- **G3** Remote OSC 133/OSC 7 bootstrap exists but is never sent; remote command exit/duration/cwd are only available if the remote shell is pre-configured. [VERIFIED]
- **G4** Commands typed in raw mode (full-screen apps, password prompts, manually run `tmux`), commands run by `tmux` outside Bilterm's view, and anything before attach are not recorded. Remote `history`/tmux server state are not read.
- **G5** A local pane where the user typed `ssh host` is not an SSH pane to Bilterm (no `remote_target`).
- **G6** History records lack host/transport/cwd/exit; `pane_id` is not globally unique; `PaneJournalRecord` loses `remote_target`; restored SSH panes are local shells.
- **G7** Headless daemon holds no live SSH/tmux PTYs; registry there reflects fed/restored data only.
- **G8** `cd` tracking and `resolve_cwd()` give wrong (local) cwd for SSH panes.
- **G9** tmux version dependence: the `pane_command_*` format variables (OSC 133 timing/status only, no command text) and control-mode flow control need a recent tmux; minimum version not verified [ASSUMED 3.4+].

## 7. Pitfalls for the planner
1. Do not index `resolve_cwd()` for non-local transports. 2. Do not store anything captured while `is_password_prompt()` or from raw-mode panes; redact like `TrafficBus` does. 3. `TmuxControlBridge::new()` hard-maps `%0 -> pane 1`; any registry that trusts `bilterm_to_tmux` on a fresh bridge will mislabel pane 1 as tmux. 4. `drawer.rs:539` marks a pane tmux by `title.contains("TMUX")`; a user-renamed pane or a title set via OSC 0/2 can flip it; use a structured field. 5. Fleet node names embed pane id (`{profile}-#{id}`, `tmux-{dest}-{session}`) and `remove_pane_references` deletes nodes when their panes close (`src/remote/mod.rs:347-356`); the registry must not rely on fleet nodes surviving a pane. 6. Pane ids are unique per `WindowManager` run only. 7. New `.rs` files must stay under the ARCH-R04 soft target; put registry code in a new `src/wm/registry*.rs`, not in `src/tmux/mod.rs` (490 lines) or `src/remote/mod.rs` (480 lines). 8. Tests: use `WindowManager::new_headless` + `TmuxControlSubprocess::from_channels` (pattern at `tests/vt_worker_and_snapshot_seam.rs:270-300`) to feed `%begin/%end` replies; no live tmux/ssh required.

## 8. Environment availability
Not probed (research was read-only, no installs). `tmux` and `ssh` binaries are needed only for optional live probes (`ssh -T host tmux -CC ...`); unit/integration tests already stub transport via `from_channels` and `new_headless`.
